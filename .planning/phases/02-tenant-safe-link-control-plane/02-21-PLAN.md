## Delivery implementation invariants

PostgreSQL owns retry attempts and lease recovery. Redis publication failures do not consume a send attempt; Asynq retries are disabled for invitation references. Preparation/render failures and completed provider attempts consume the eight-attempt SQL budget. Each provider attempt has a ten-second deadline.

Before Redis publication, the worker persists the complete provider request (recipient, sender, subject, rendered HTML and idempotency key) inside the existing authenticated encrypted envelope. Retries and worker/config/template/workspace changes reuse those frozen fields. The immutable delivery-intent UUID identifies message content; lease generation only fences concurrent processing. A future resend must replace the intent UUID or introduce an explicit immutable content generation, rather than reuse a lease generation as the provider message identity.

Keep every encryption key needed by queued, leased or retained failed ciphertext available to the worker until that ciphertext drains or is safely re-encrypted. Successful acknowledgement atomically commits Delivered and erases the entire ciphertext. Provider acknowledgement followed by a database crash remains uncertain: retry uses the same request and provider key, but deduplication beyond the provider's retention window is not guaranteed.

The default invitation adapter uses only fixed HTTPS Resend transport without environment proxy selection. Local actual-HTTP acknowledgement tests establish the durable worker boundary; live-provider delivery and inbox acceptance remain 02-35 evidence.
